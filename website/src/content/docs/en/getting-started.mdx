This page offers two paths: **run the full stack with Docker** (recommended — no local Rust or Node
toolchain), or **run it from source** when you need to change code. Both end with the same discovery check.

## Requirements

With Docker you only need:

- Docker Engine with Compose v2 (`docker compose`)
- Outbound `UDP/123` from the container — the security clock is verified at startup and the service exits if it fails

Running from source additionally needs:

- A Rust toolchain (matching the workspace edition and dependencies)
- Node.js ≥ 22.23.4 and pnpm 10+

Production needs HTTPS and trusted NTP sources.

## Run it with Docker (recommended)

Images are published for `linux/amd64` and `linux/arm64`, so no local Rust or Node toolchain is needed.
The bundled Compose stack terminates TLS in Caddy, pulls the identity service from `ghcr.io`, and keeps
PostgreSQL on an internal network with no published host port.

```bash
git clone https://github.com/Bin-hy/yufu.git
cd yufu/deploy/docker

cp env.example .env
cp yufu.toml.example yufu.toml
mkdir -p state
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 \
  -out state/oidc_rsa_private.pem
chmod 600 state/oidc_rsa_private.pem
```

Replace every `CHANGE_ME` value in `.env` — at least `POSTGRES_PASSWORD` and `AUTH_SECRET` — and point
the image at the published build so nothing is compiled inside the container:

```dotenv
YUFU_DOMAIN=localhost
YUFU_HTTPS_PORT=8443
YUFU_IMAGE=ghcr.io/bin-hy/yufu:latest
```

`issuer` and `[auth].origins` must both name the address the browser actually uses. If they disagree,
logins redirect incorrectly or the API rejects requests on the origin check:

```toml
[auth]
origins = ["https://localhost:8443"]

[oidc]
issuer = "https://localhost:8443"
```

Pull the image and start the stack:

```bash
docker compose pull yufu
docker compose up -d --no-build
docker compose ps
```

Open `https://localhost:8443` and sign in with the `[auth.super_admin]` account. The first start runs
the versioned database migrations.

:::caution
Inside a container the service can only listen on `0.0.0.0`, so `--allow-insecure-loopback-cookies`
is unusable and the public entry point must be HTTPS. For local trials Caddy signs a certificate with
its own local CA, which the browser will report as self-signed. Keep `state/oidc_rsa_private.pem`:
replacing it invalidates issued tokens and every registered client.
:::

Domains, certificates, backups, upgrades and troubleshooting are covered in
[container deployment](/en/operations/docker/).

## Run it from source

Take this path when you need to change code or want to debug with a local toolchain.

### 1. Get the code and dependencies

```bash
git clone https://github.com/Bin-hy/yufu.git
cd yufu
pnpm install --frozen-lockfile
```

### 2. Start the database

`compose.yaml` only provides the identity PostgreSQL instance, mapped to local port `5433`:

```bash
docker compose up -d
```

The default database is `yufu`, with `postgres` as both user and password.
Replace these credentials in production.

### 3. Prepare the configuration

```bash
cp conf/yufu.example.toml conf/yufu.local.toml
```

At minimum, review these fields:

```toml
[http]
listen = "127.0.0.1:4000"

[auth]
secret = "replace with a long random value"

[auth.super_admin]
username = "admin"
password = "replace with a strong password"

[oidc]
issuer = "http://127.0.0.1:4000"
rsa_private_key_path = "conf/oidc_rsa_private.local.pem"

[database]
url = "postgres://postgres:postgres@localhost:5433/yufu"

[security_clock]
servers = ["time.apple.com:123", "time.cloudflare.com:123"]
min_agreeing_sources = 2
```

:::caution
`--allow-insecure-loopback-cookies` is for local HTTP only. It requires both the listener and the
issuer to be loopback. Production must use HTTPS and the default secure cookies.
:::

### 4. Start the service

```bash
pnpm build:web
cargo run --bin yufu --features webui -- \
  --config conf/yufu.local.toml \
  --allow-insecure-loopback-cookies
```

`--features webui` embeds the frontend build from `assets/web`, so run `pnpm build:web`
first. Versioned database migrations run automatically at startup.

### 5. Sign in for the first time

Open:

```text
http://127.0.0.1:4000
```

Sign in with the account from `[auth.super_admin]`. After signing in you can reach:

- `/account`: profile; `/account/apps`: accessible applications; `/account/consents`: data consent; `/account/sessions`: login sessions
- `/developer/*`: registration, configuration, versions, and approvals for your applications
- `/admin/*`: accounts, applications, groups, assignments, approvals, and audit

Navigation follows account qualifications: all members have the account center, qualified developers
have the developer console, and enterprise administrators have enterprise administration.
The workspace is at `/dashboard`. See the [console guide](/en/guides/console/) for screenshots and workflows.

### 6. Verify discovery

```bash
curl -s http://127.0.0.1:4000/.well-known/openid-configuration | jq .
curl -s http://127.0.0.1:4000/.well-known/jwks.json | jq .
```

Health check:

```bash
curl -s http://127.0.0.1:4000/api/v1/health/ready | jq .
```

Authentication is ready only when `security_clock_synchronized` is `true`. When the clock check fails,
authentication endpoints return 503.
