## One issuer for every identity entry point

<p class="lead">
  yufu is a single-tenant identity and SSO platform that you deploy yourself. The account center,
  developer console, and enterprise admin console are one product. Application onboarding is
  invitation and approval based; there is no public application marketplace.
</p>

<CardGrid>
  <Card title="Standard OIDC / OAuth 2.0" icon="approve-check">
    Discovery, Authorization Code + PKCE, UserInfo, Introspection, Revocation, RP-initiated logout, and back-channel logout.
  </Card>
  <Card title="Single-tenant SSO" icon="lock">
    One issuer serves every internal application. Sign in once, move across applications within your grants, and log out with session linkage.
  </Card>
  <Card title="Fine-grained authorization" icon="setting">
    Roles, URI permissions, application permissions, and PDP decisions. Application access is never granted by default.
  </Card>
  <Card title="Sessions and revocation" icon="refresh">
    Refresh-token rotation, revocation generations, device and session management, with every administrative write audited.
  </Card>
  <Card title="Self-hosted" icon="server">
    One Rust binary plus PostgreSQL. Start with Docker Compose, then run it under systemd or a container platform.
  </Card>
  <Card title="Reference implementations" icon="puzzle">
    A Go runtime SDK plus confidential web and public SPA examples covering login, protected APIs, and logout linkage.
  </Card>

## Why "yufu"

<p class="lead">
  yufu is the pinyin of <strong>鱼符</strong> (yúfú): the fish-shaped identity token that Tang-dynasty
  officials carried on their person. It was cut in two — one half kept at court, one half carried —
  and only counted once the halves were joined. Gold, silver and copper marked three ranks of authority.
</p>

That object is the act of authentication itself: holding one half is not an identity, matching the two is.
Our mark is therefore a fish split by a seam — **apart a token, together an identity**. And "three ranks"
is the reminder that recognising who you are is not enough; the system also has to know how far you may go.

<CardGrid>
  <Card title="One identity, not a pile of accounts" icon="lock">
    A fixed issuer, one sign-in for every authorised application. Internal apps no longer keep a
    password store of their own.
  </Card>
  <Card title="Access is granted explicitly" icon="approve-check">
    Applications join through enterprise invitation and approval, and which applications a member
    may reach is assigned explicitly — there is no "registered, therefore visible". Unsupported
    execution credential profiles fail closed.
  </Card>
  <Card title="Credentials can be withdrawn" icon="refresh">
    Refresh-token rotation, sessions terminated per centre or per application, logout delivered over
    back-channel where the application supports it, and every grant and revocation written to audit.
  </Card>
  <Card title="The keys stay with you" icon="server">
    One Rust binary plus PostgreSQL, with the console embeddable in the binary. The signing keys, the
    database and the audit trail all belong to the deployment.
  </Card>
</CardGrid>

## Running in five minutes

Local development needs Docker, Rust, and pnpm. Compose provides the database, and versioned migrations run at startup.

Open `http://127.0.0.1:4000` after the first start and sign in with the super administrator from your configuration.

See [Quick start](/en/getting-started/) for every configuration key, production deployment, and the full integration flow.

</div>
<div>

```bash
git clone https://github.com/Bin-hy/yufu.git
cd yufu

pnpm install --frozen-lockfile
pnpm build:web
docker compose up -d

cp conf/yufu.example.toml conf/yufu.local.toml
cargo run --bin yufu --features webui -- \
  --config conf/yufu.local.toml \
  --allow-insecure-loopback-cookies
```

## Standard protocols, explicit boundaries

<p class="lead">
  Only a verified protocol subset is implemented: authorization code, PKCE S256, refresh-token rotation,
  and standard logout. Multi-tenancy, external IdP federation, SAML/LDAP/SCIM, and MFA are out of scope.
</p>

| Endpoint | Path | Notes |
| --- | --- | --- |
| Authorization | `/oidc/authorize` | `response_type=code` with PKCE `S256` only |
| Token | `/oidc/token` | `authorization_code` and `refresh_token` |
| UserInfo | `/oidc/userinfo` | Bearer access token |
| Introspection | `/oidc/introspect` | Reader credentials |
| Revocation | `/oidc/revoke` | Access and refresh tokens |
| End session | `/oidc/end-session` | RP-initiated logout, published with RS256 |
| Discovery | `/.well-known/openid-configuration` | Endpoints and capabilities |
