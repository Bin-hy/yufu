# Go SDK 独立仓库迁移 Spec

## 背景

Go Runtime SDK 当前随服务端仓库维护，文档中的独立安装地址已写好，但实际源码尚未迁移。用户已创建 GitHub 仓库 `Bin-hy/yufu-sdk-go` 和本地空目录 `/Users/binhy/Binhy-Projects/yufu-sdk-go`，要求迁移并删除服务端仓库中的 SDK。

## 目标

让 SDK 在独立仓库中维护、测试和分发，同时保持现有调用方式和服务端联调示例可用。

## 功能需求

- F1：完整迁移 SDK 源码、内部组件、现有测试和使用说明，保留当前公开接口与模块标识。
- F2：在确认目标文件完整且独立测试通过后，删除服务端仓库内的 SDK 实现。
- F3：服务端保留现有 Web 联调示例，改为依赖独立 SDK，解除对已删除目录的依赖。
- F4：更新服务端 README、中英文 SDK 指南和独立 SDK README，准确说明仓库位置、安装、测试及本地联调方法。
- F5：独立仓库具备运行现有测试与静态检查的 CI，并保留适用的原项目许可证信息。
- F6：准备独立仓库的 Git 配置，关联用户指定的 GitHub 仓库；远端同步状态与可用安装版本必须据实报告。

## 非功能需求

- N1：迁移不改变认证协议行为、公开接口或最低 Go 版本。
- N2：保留已有用户文件；目标目录目前为空，后续如出现文件必须先检查，不能覆盖未知内容。
- N3：历史设计文档和已归档验收证据保持原样；只修正当前使用说明。
- N4：验证通过后才删除原副本，避免迁移丢失。

## 不做的事

- 新增 SDK 功能或修复无关服务端问题。
- 搬迁服务端本身及其 Docker 联调基础设施。
- 重写历史提交或修改仓库可见性。

## 验收标准

- AC1（F1、F2）：迁移前后 SDK 实现和已有测试内容一致，独立目录运行现有测试、竞态检测及静态检查通过，服务端原 SDK 目录已删除。
- AC2（F3）：服务端示例不再引用已删除目录，现有离线契约测试和静态检查通过；真实联调入口仍保留。
- AC3（F4）：当前使用说明中的源码链接指向独立仓库，不再要求使用服务端内的 SDK 路径。
- AC4（F5）：独立仓库包含许可证与 CI，CI 执行现有测试及静态检查。
- AC5（F6）：独立仓库远端地址正确，最终报告明确本地验证、远端提交及安装验证各自的实际状态，未发布的版本不写成可安装版本。
