# OIDC subject 字符串类型修复 Spec

## 背景

当前 UserInfo 响应和 ID Token 中的 subject（`sub`）输出为 JSON 数字，不符合 OIDC 对字符串类型的要求。Access Token 和令牌内省响应已经使用字符串。

## 目标

- 将对外 OIDC subject 统一为字符串，保持现有用户身份对应关系。
- 覆盖首次授权与刷新流程，防止类型问题再次出现。

## 功能需求

- F1：授权码兑换和刷新流程签发的 ID Token 中，`sub` 必须为字符串；RSA 与 HMAC 签发路径均满足要求。
- F2：UserInfo 响应的 `sub` 必须为字符串，并与同一用户的 ID Token subject 完全一致。
- F3：现有整数用户 ID 按十进制表示输出，例如用户 123 输出 `"123"`，不添加前缀，不改变用户身份映射。
- F4：项目内 OIDC 客户端的 UserInfo 类型声明采用字符串，现有本地数字用户 ID 的业务使用继续正常工作。

## 非功能需求

- N1：数据库用户 ID、关联字段及内部业务 ID 保持原类型，无需数据迁移。
- N2：Access Token、令牌内省和现有刷新令牌的处理保持兼容。
- N3：协议声明与签发入口约束 subject 为字符串，避免将数字直接序列化到 ID Token。
- N4：已签发 ID Token 不作原地修改；刷新或重新登录后获得符合新类型约定的 ID Token。外部客户端若依赖数字类型，需要同步调整。

## 不做的事

- 不引入 UUID、成对 subject 或新的用户标识映射。
- 不扩展到其他 OIDC 合规性或鉴权问题。
- 不变更内部旧登录流程使用的刷新令牌载荷类型。

## 验收标准

- AC1（F1）：验证 RSA 和 HMAC 签发出的 ID Token，载荷 `sub` 为 JSON 字符串。
- AC2（F1、F2）：通过授权码兑换、UserInfo 查询与刷新流程，确认前后 ID Token 和 UserInfo 中的 `sub` 均为字符串且完全一致。
- AC3（F3）：使用已知整数用户 ID，验证输出等于其十进制字符串表示。
- AC4（F4）：前端类型检查通过，加载字符串 subject 的用户信息后仍可获取原本的本地用户 ID。
- AC5（N1、N2）：受影响 Rust crate 编译及相关回归测试通过，不包含数据库迁移，现有令牌刷新行为通过验证。
