# Tag 自动打包与发版 Spec

## 背景

项目已有 main 分支及 PR 的三平台 CI，但没有 tag 触发的安装包与 GitHub Release 流程。
发布对象为 yufu 身份服务，管理前端需要先构建并嵌入二进制。
官网通过现有 Cloudflare Pages 流程维护。

## 目标

推送版本 tag 后，自动验证、构建和打包各平台产物，并在全部成功后发布 GitHub Release。
提供可识别版本与目标平台的安装包、配置模板、使用说明及 SHA-256 校验文件。

## 功能需求

- F1：推送 `v主版本.次版本.修订版本` 或带 `-alpha.N`、`-beta.N`、`-rc.N` 的 tag 时触发发布；其他 tag 不发版。
- F2：构建被标记的提交，并核对 tag 版本与 Rust workspace 声明版本一致；不一致时失败并给出修正提示。
- F3：发布前执行 Rust 格式、Clippy、单元/集成与文档测试，以及控制台 test/check/lint；集成测试使用隔离 PostgreSQL。
- F4：提供 Linux x86_64、Windows x86_64、macOS x86_64、macOS ARM64 四个平台包，每个包包含可执行的 yufu 和内嵌 WebUI。
- F5：Linux/macOS 使用 `.tar.gz`，Windows 使用 `.zip`；文件名包含产品、tag 与目标平台。
- F6：包内提供配置示例和发布使用说明；Linux 另附 systemd 模板。不得包含本地配置、数据库、私钥、真实凭据或 node_modules。
- F7：对安装包生成统一的 `SHA256SUMS` 文件；验证压缩包目录、可执行文件和版本输出。
- F8：所有验证及平台构建成功后，才向 GitHub Release 上传完整产物并发布；任何前置任务失败均不发布可见 Release。
- F9：稳定版本生成正式 Release；alpha、beta、rc 生成 prerelease。发布说明包含自动生成的变更记录及安装/校验提示。
- F10：同一 tag 的重复执行不覆盖已公开发布的产物；失败后允许处理未发布草稿并重试，防止并发发布同一版本。
- F11：README 提供下载入口、各平台包说明、版本准备、创建/推送 tag 与校验下载的步骤。

## 非功能需求

- N1：默认仅授予只读仓库权限，只有最终发布任务获得 Release 写权限。
- N2：前端和 Rust 构建遵循已提交的依赖锁文件；各平台依赖及运行环境要求明确记录。
- N3：敏感权限仅用于发布本仓库 tag，不用于 PR 或不可信输入执行；tag 值以数据形式传递。
- N4：构建日志和产物清晰标注来源 tag、提交和平台，不声称已经在未实际执行的平台验收通过。
- N5：保留现有 CI，新增独立发布流程；任何不相关的 README 工作区修改均需保留。

## 不做的事

- 本次不创建或推送真实版本 tag，不实际发布第一个 Release。
- 不发布 Docker 镜像、Cargo crate、npm 包、Go SDK 独立版本或官网部署。
- 不提供 Linux ARM64、musl 静态版本、安装器、自动更新和代码签名/公证。
- 不改动业务逻辑，不自动提升仓库版本或替用户提交版本变更。

## 验收标准

- AC1（F1、F2）：合法稳定/预发布 tag 正确识别；非法 tag、版本不一致在构建/发布前被拒绝。
- AC2（F3）：工作流明确执行所列检查；任意检查失败时发布任务不执行。
- AC3（F4、F5）：构建矩阵覆盖四个目标，先构建前端再嵌入；各包格式和名称符合约定。
- AC4（F6）：解包后可找到二进制、配置示例和说明，Linux 含服务模板；包中无敏感或开发环境文件。
- AC5（F7）：每个平台二进制可输出与 tag 一致的版本；所有下载包均有可验证的 SHA-256。
- AC6（F8、F9）：最终发布依赖全部检查和构建；先暂存完整草稿，再按稳定/预发布类型公开。
- AC7（F10）：已公开版本不可被重跑覆盖；同 tag 执行互斥；未完成草稿有明确重试策略。
- AC8（F11）：README 的版本准备、tag 命令、下载和校验步骤可按顺序执行，链接和包名与工作流一致。
- AC9（N1—N5）：静态检查通过；实际执行的平台与未在 GitHub 运行的部分分别记录，不把本地验证冒充跨平台运行结果。

## 待审批方案

推荐按上述四平台范围实现。通过本 Spec 后，依次细化技术设计、任务拆解和验收清单。
